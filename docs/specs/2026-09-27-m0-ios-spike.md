# M0 iOS Benchmark

## Scope

Continue the desktop feasibility experiment with one hardcoded Choice request in a minimal iOS app.
Use the same pinned model, renderer, verdict readout and upstream native Scorer.
Keep this experiment under `spikes/m0/ios/`; production C APIs, Flutter bindings and remote routing remain deferred.

## Behavior

Prepare token IDs with the verified Python renderer on the Mac.
Bundle the verified Q4_K_M model, request and license notices into a locally generated app.
Verify bundled model and fixture SHA-256 before inference.
Load one context, reset its memory before every request, and record the first request separately from 20 warm samples.
Time native scoring, its internal memory resets and verdict softmax; exclude the outer reset, tokenization, resource hashing, model loading and report export.
Preserve every native response, distribution and duration in an exported JSON report.

## Acceptance

- Missing samples, nonfinite scores, inconsistent probabilities, pin drift and fixture drift fail report validation.
- The in-process C++ path agrees with the desktop Choice reference within the unchanged strict `1e-3` gate.
- An unsigned iOS arm64 Release app builds against the pinned native source.
- Simulator evidence is labelled as simulator evidence and never satisfies the physical-device measurement.
- Report validation checks declared hardware, OS, Release/arm64 receipt, pinned inputs and timing boundaries; metadata alone never proves physical execution.
- The physical CLI gate rejects CPU-only, modified or missing backend metadata; require the default requested Metal profile with both offloads enabled and neither diagnostic switch requested.
- Report validation requires the fixed context profile: `n_ctx=2048`, `n_batch=2048`, `n_ubatch=1024`, `n_seq_max=2`, `n_outputs_max=16`, `threads=4`, and `flash_attn=auto`.
- The physical CLI gate requires exactly 20 warm samples; shorter or longer diagnostic reports cannot satisfy it.
- Physical-device acceptance requires an observed approved run/export from the connected iPhone, comparison with the local build receipt, and 20 warm samples before M0 is declared complete.

## Authority and Constraints

The operator requested continued implementation.
The explicit PR-loop invocation authorizes local preparation, tests, builds, scoped commits, push, PR publication and review replies.
It does not authorize merge or physical-device installation and launch.
The daily iPhone requires explicit installation and launch approval after the app is reviewable.
Keep heavy builds and simulator work sequential and reuse an already booted simulator.
Oracle found no project-specific scorer precedent; `wiki/concepts/mac-mini-resource-limits.md` confirms those execution constraints.
